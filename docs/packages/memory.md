# `memory`：长期记忆

记忆系统自行设计，不直接采用某一个现成系统。本包只管从 session 记录里提炼出来、跨 session 使用的长期记忆；session 记录本身由 [session-store](session-store.md) 保存。本包只在 Host 一侧使用，runtime 经通道检索和提议记忆（见 agent-runtime 的[通道](agent-runtime.md#通道)）。P3 交付。

## 两种范围

| 范围 | 存什么 | 用途 |
|---|---|---|
| Project | 架构决策、项目约束、测试命令、失败过的尝试及原因 | 在同一项目的不同 session 之间复用 |
| User | 个人偏好、协作习惯 | 只属于这个用户，可以跨项目使用 |

范围决定"谁能用、在哪里用"；内容类型（事实、偏好、决策、经验）是另外的属性，两种范围共用一套记录格式和接口。当前 session 的内容不另存一份"session 记忆"：继续当前任务、压缩上下文和恢复都直接用 session 记录。

## 模块

```text
memory/
  core/        记录格式：范围、来源、状态、纠正和删除规则
  long-term/   长期记忆的提取、整理和检索
  storage/     本地存储和索引，以及数据迁移和导出
  sdk/         对外接口：记录、检索、纠正、遗忘、导出
```

## 要点

- session 记录里的内容经过筛选和确认才能成为记忆（见[写入](#写入)）。session 记录由 Host 从 session-store 读出后交给本包，本包不依赖 session-store。
- 每条记忆记下内容来自用户本人的表述，还是来自文件、网页、工具输出等不可信内容；不可信内容不能自动成为 user 记忆，否则一个仓库里的注入内容会随 user 记忆进入别的项目。
- 每条记忆都记下来源：哪次会话、哪些文件、哪个 commit。相关代码变化后要重新核实。
- Project 记忆按 Host 判断的项目身份隔离（见 agent-host 的[项目身份](agent-host.md#项目身份)），不采信仓库内容自己声明的身份。
- 范围落实到实际的存储空间，读、写、改、删都检查范围，不能只在查询时按附加字段过滤，否则抽取步骤就会看到同一用户别的项目的记忆。
- "不再使用"、"标记过期"和"彻底删除"是三种不同操作。彻底删除要覆盖记忆本身、它的历史版本、索引、缓存和本包做的迁移备份；重建索引时不能把已删除的内容找回来；用户导出的文件由用户自己保管，不在删除范围内。用户要求忘记的内容如果也出现在 session 记录里，由 Host 同时让 session-store 按事件脱敏（见 session-store 的[要点](session-store.md#要点)）：彻底删除一条记忆时，Host 把它和它的各个版本记下的来源事件，连同按记忆的编号找到的它的标题和正文的副本（索引、"记忆更新"、自动注入的正文、检索结果、候选列表），一起脱敏；user 记忆在每个登记过的项目里找。做法和脱敏不了的情况见 agent-host 的[按事件脱敏](agent-host.md#按事件脱敏)。交给模型的每一份都以 `[编号]` 开头，副本靠它找：改记忆交给模型的写法时保留这个标记。
- 不内置默认的存储位置，所有位置都由调用方显式传入，并通过重启测试。
- 提取和整理要调用模型时，由调用方传入发起调用的函数：Host 用模型代理的那份模型定义和凭据发出请求，凭据不进本包。疑似密钥的内容不写入，检测函数由调用方传入（Host 的 `redaction/`）。
- 多个 worker，或同一项目不同 worktree 上同时运行的 Host，同时更新同一条记忆时要能发现冲突，不能悄悄覆盖。
- 只返回带来源的结果；要不要放进模型上下文、放多少，由 runtime 决定。放进上下文时标明来源，和用户当前的明确要求冲突时以当前要求为准。

## 记录格式

每条记忆包含类型（事实、偏好、决策、经验）、一行标题、简短正文、状态（待确认、生效、不再使用、已过期）、内容来自用户本人还是不可信内容、来源（具体到 session 里的事件，以及文件路径和行号、内容哈希、commit；路径相对项目根目录保存，换一个 worktree 也能核对；来源事件被到期清理后标为"来源已删除"；user 记忆不记引用的文件，相对某个项目根目录的路径在别的项目里核对不了）、版本号、确认时间和最近使用时间；范围由所在的数据库文件决定（见[存储](#存储)）。标题不超过 120 个字符、正文不超过 2,000 个字符，超出的直接拒绝：索引和检索结果都要放进上下文。正文写明依据（实际运行验证过、用户说的，还是推断）和适用条件，命令、路径和报错照原文写：记忆是给以后的会话用的，读到的时候要能判断还能不能信。每次改动（确认、纠正、改状态）版本号加一，内容变了的版本保留全文。P3 不建向量和全文索引，不设按时间到期，不做全局整理，等评测显示有收益再加。

## 写入

写入有三个入口：用户在 CLI 里直接添加；模型在任务中调用 `memory_propose` 提议；Host 打开同一项目的新 session 时，从旧 session 记录里后台提取。

- 除了用户在 CLI 里亲手输入的内容，其余都只生成"待确认"的候选，由用户在 Host 一侧确认，project 和 user 两种范围相同。交互模式在 task 结束时列出候选，用户可以确认、修改后确认或拒绝；非交互运行时候选保持待确认，不自动生效，用户之后用 `/memory` 处理。
- project 记忆也要确认：候选是模型综合整个上下文写出的，Host 无法可靠判断它只来自用户，写进记忆后会出现在之后每个 session 的开头；不经批准的记忆写入已有被注入内容利用、持续外泄数据的先例。
- `memory_propose` 是 runtime 的内置工具，只给主 agent（见 agent-runtime 的[工具执行](agent-runtime.md#工具执行)）。不只记用户明确要求的内容：那会漏掉测试命令、失败尝试这类 project 记忆的主要内容；这种做法保留为评测里的一种写入策略。
- 候选的来源是这次 `memory_propose` 调用的事件：runtime 先登记调用、再经通道提交候选，没有登记就提交的按协议错误处理。引用了项目根目录之外的文件的候选直接拒绝，原因交给模型：之后的 session 核对不了它。
- 工具说明和提取指令只写明记忆的用途（让以后的会话不用重新摸索），值不值得记由模型判断，不规定只记哪几类：写死的类别会漏掉有用的内容。只写明两种不记：没有验证过的猜测，和能从仓库当前内容直接读到的东西；条目少而准，索引才有用。
- 候选可以指明它要取代的现有记忆，`memory_propose` 和后台提取都可以：确认后成为那条记忆的新版本，不新增一条。同一件事只留一条，索引不随 session 数增长。
- 模型写出的候选一律记为来自不可信内容；用户直接添加、修改后确认和纠正的内容记为来自用户。
- **后台提取**：交互模式下，Host 打开一个 session、agent 进程完成握手后，处理同一项目里关闭后空闲 6 小时以上、最近 10 天内、还没提取过的 session，每次最多 2 个；非交互模式不做，免得在 `--max-cost` 之外花钱。
  - 提取在 Host 里进行：把 session 记录交给本包，去掉规则文件和 skill 的内容，也跳过分叉从父 session 继承来的事件；本包经调用方传入的函数用当前 session 选用的模型调用模型，不启动 agent 进程、不用工具，和当前的 task 并行。
  - 每次提取只受固定的上限约束：1 美元、20 次请求；上限用完时到此为止，已经得到的候选照常记下。它的事件记在当前 session 里，属于一个不在任何 task 里的 run（见 session-store 的[事件格式](session-store.md#事件格式)）：只记开始和结束两条（`memory.extraction.started`、`memory.extraction.ended`，后者带结果、候选的编号和用量），不记交给模型的记录和模型的回复，否则来源 session 的内容会在当前 session 里多出一份，删除来源 session 时删不干净。用量并进当前 session 的合计。
  - session 的写锁没有被活着的 Host 持有就算已关闭。开始前在这个项目的记忆库里写一条带 Host pid 的认领记录，同一项目另一个 worktree 上的 Host 跳过已认领的 session。"已提取"的标记也记在记忆库里，不写进来源 session：写入会延长它的保存期限。session 关闭时先取消进行中的提取，被取消的来源 session 不标为已提取；失败和超出上限的照常标记，不在每次打开 session 时为同一个 session 重复花钱。
  - 提取时把两种范围内生效记忆的标题和正文一起交给模型：记录推翻了某条记忆时，可以提出纠正它或把它"标记过期"的候选，同样待确认。错的记忆只在用到它的会话里暴露，不在这时纠正就会一直留着。
  - 提取的候选只带文件路径，不带内容哈希：Host 不读仓库源文件。
  - 得到的候选同样待确认，在下一个 task 结束时和其他候选一起列出。
- 评测比较写入方式时，由 evaluation 通过 Host SDK 按脚本确认候选，产品不加"自动确认"开关。
- 入库时中和不可见字符和伪装成系统标记的内容，并拒绝含密钥的候选。

## 检索

自动放进上下文的只有一份短索引，正文由模型按需取得。

- session 开始时，Host 把当前 user 范围和 project 范围内生效记忆的索引作为启动配置交给 runtime（见 agent-runtime 的[从 Host 得到的配置](agent-runtime.md#从-host-得到的配置)）：每条只有标题、类型、来源和"引用已改动"标记，总长不超过 2,500 token（按 UTF-8 字节数除以 1.7 估算，同 api 的 [token 计数](api.md#token-计数)）。超出时按最近使用和确认的时间从新到旧保留，末尾注明还有几条没列出、可以用 `memory_search` 查找：没列出的条目模型要知道还查得到。runtime 把它放进会话开始的上下文消息，排在规则文件和 skills 列表之后，注明"来自过去的会话，可能过期，用前按引用核实"，不放进系统指令。系统指令里只有一段固定的说明：记忆的用途，以及依赖某条记忆之前先用 `memory_read` 读正文；不提示时便宜的模型常常只看标题，或者有索引也不去读。
- 正文由模型调用 `memory_search`、`memory_read` 按需取得，不在每个 task 开始时自动注入：选错的记忆有害，VibeMemBench 里统一注入检索结果的 12 组"系统 × 模型"组合有 11 组不超过无记忆。这两个工具只给主 agent。
- session 中新确认、停用或删除的记忆，在下一个 task 开始时以"记忆更新"追加：Host 在每个 task 开始前生成当前的索引，和上次发给 runtime 的不一样就发过去（`config/update`），同一项目另一个 Host 做的改动也带得上；runtime 和已经告诉模型的索引比较，只追加差别。告诉过模型的索引随 `instructions.recorded` 记进 session 记录，重启 agent 进程后照它比较。
- `memory_search` 把查询拆成词（按空白和标点，中日韩文字按相邻两字），逐条在标题和正文里做不区分大小写的子串匹配，按命中的词数、再按确认时间排序，最多返回 5 条，带正文；整句都命中的排在最前。`memory_read` 按编号返回正文和来源。两者返回的条目都更新最近使用时间，引用的文件由 runtime 重新核对哈希。
- 不采用 Anthropic 的 `memory_20250818` 工具：它只属于 `anthropic.messages`，还会在系统提示里自动加指令。

## 和规则文件的关系

project 记忆不写进规则文件（`AGENTS.md` 等），memory 包和 Host 都不自动修改规则文件。

- 规则文件是仓库内容，随版本库共享给团队和其他 agent；记忆属于本机和个人，还可能含不可信来源，自动写入等于把模型输出推进团队共享的指令。用户想固化某条记忆时，让 agent 用普通编辑工具修改规则文件，照常经过 Permission，再把这条记忆设为"不再使用"。
- 冲突时以用户当前的明确要求为准，其次是规则文件，最后是记忆。runtime 不自动比较记忆和规则文件（索引只有标题，判断冲突要语义比较）：模型发现某条记忆和规则文件冲突时按规则文件执行，并在回复里提示用户处理这条记忆；user 记忆和某个项目的规则文件冲突时，在这个项目里按规则文件，在其他项目照常使用。这里的优先级只管行为约定，两者都不能改变权限。
- 提取记忆时去掉规则文件和 skill 的内容，也不保存规则文件已经写明的内容。

## 查看、纠正和删除

CLI 的 `/memory`（见 agent-host 的[会话内命令](agent-host.md#会话内命令)）和 Host SDK 提供同一组操作：列出、查看正文和来源、确认或拒绝候选、直接添加、纠正、"不再使用"、"标记过期"和彻底删除。

- 纠正生成新版本，旧版本保留到彻底删除为止，可以回滚，纠正后的内容记为来自用户。"不再使用"的记忆不再返回给 runtime，可以恢复；"标记过期"表示内容曾经成立、现在不成立，不进索引也不返回，纠正后重新生效；彻底删除清除记忆、全部版本、来源和索引。
- 列表明确显示每条的状态，不把隐藏当作删除。用户不直接编辑存储文件，所有修改都经过命令，范围检查、来源记录和冲突检测才能生效。
- **引用的核实**：每条记忆记下引用文件的内容哈希和 commit。Host 不运行 git，也不读仓库源文件：写入时，候选里引用文件的哈希由 runtime 在沙盒里计算并随 `memory_propose` 提交，commit 由 Host 读 git 目录里的 `HEAD` 得到，用户在 CLI 直接添加的记忆不带文件哈希；session 开始时，runtime 在 agent 沙盒里按 Host 给出的路径和期望哈希核对，不符的在索引上标"引用已改动"，由模型按引用核实，纠正还是标记过期由用户决定。
- 不设按时间到期：记忆都经过确认才生效。记下最近使用时间，留给评测判断是否需要。
- 被删除的 session 作为来源时：用户主动删除 session，只删除来源事件真的被删掉的记忆（事件被改记到分叉名下的不算，来源随事件一起改记）；到期清理只把来源标为"来源已删除"（见 session-store 的[保存期限](session-store.md#保存期限)）。

## 存储

和 session-store 用同一个 SQLite 绑定（`node:sqlite`），但表结构和数据库文件分开：user 范围一个文件 `data/user/memory.sqlite`，每个 project 一个文件 `data/projects/<project_id>/memory.sqlite`，路径由 Host 传入。

- 按范围分文件后查询不可能跨范围，删除一个项目的全部记忆就是删除它的文件，评测的无记忆组也不打开任何记忆库。
- 连接时显式设 WAL、`busy_timeout=5000`、`secure_delete=ON` 和 `synchronous=FULL`。更新带版本号，`UPDATE … WHERE id = ? AND version = ?` 没有改到行就报冲突。
- 迁移照 session-store 的做法：格式版本记在 `PRAGMA user_version`，迁移前用 `backup()` 做备份，成功后删除备份（见 session-store 的[存储格式](session-store.md#存储格式)）。
- 不以 Markdown 文件为本体：要记来源、状态和版本，彻底删除时也不能留下副本；导出时再生成 Markdown 或 JSONL。
- 检索逐条做子串匹配，不建索引：向量索引要额外调用嵌入模型；FTS5 的 `unicode61` 分词搜不到中文子串、`trigram` 搜不到两个字的词，用了 FTS5 时彻底删除还要额外处理。
- 彻底删除覆盖到数据库文件这一层：记忆、全部版本和针对它的候选从表里删除，`secure_delete` 把腾出的页清零，随后截断 WAL，数据库文件和 WAL 里扫描不到原文。APFS 的快照、SSD 上被重映射的块和 Time Machine 这类备份里可能还有旧的页，覆盖写不等于物理擦除，不在覆盖范围内，README 里写明。

## 评测

记忆的价值要和无记忆组对比，对比组、场景和统计方法见 evaluation 的 [Memory 评测](evaluation.md#memory-评测)。本包要为评测提供：

- 完整 memory 组内部比较写入策略（只记用户明确要求的、加上模型提议、再加上后台提取）和检索方式（只给索引、只给工具、两者都给、自动注入前几条正文）。写入策略和"记忆注入方式"都是 Host SDK 创建 session 时的选项，经 `initialize` 的响应交给 runtime（见 agent-runtime 的[从 Host 得到的配置](agent-runtime.md#从-host-得到的配置)），CLI 和配置文件都不能设置。
- 后台提取平时只处理空闲 6 小时以上的 session，评测里触发不了，所以 Host SDK 另有一个只给评测用的"立即提取"操作：对指定的已关闭 session 马上运行一次提取，不看 6 小时和 10 天的条件，CLI 不暴露。
- 用检索和提议事件（`memory.retrieved`、`memory.candidates`、`memory.updated` 和记忆工具的调用）把失败归到五类：没写入、没确认、没检索到、检索到但没用、误用过期记忆；同时统计提取的 token、每个 task 的候选数和确认次数、每个 session 的索引 token。
- 安全测试在仓库文件、网页和工具输出里放注入指令，检查没有确认的内容不会生效，user 记忆不会从不可信内容自动产生，冒充的项目身份读不到别的项目的记忆，彻底删除后数据库文件里扫描不到原文。

## 可以借鉴的设计

| 项目 | 可借鉴的做法 |
|---|---|
| Engram（Gentleman-Programming/engram） | SQLite 加全文检索的轻量本地存储，按主题更新同一条记忆，会话交接摘要 |
| Hindsight（vectorize-io/hindsight） | 保存、召回、反思三步处理，保留证据的观察记录和时间推理 |
| OpenViking（volcengine/OpenViking） | 资源、用户记忆、会话分层组织，会话提交后再异步提取记忆；AGPL-3.0，只参考设计 |
