# `memory`：长期记忆

记忆系统自行设计，不直接采用某一个现成系统。本包只管从 session 记录里提炼出来、跨 session 使用的长期记忆；session 记录本身由 [session-store](session-store.md) 保存，分开的原因见那里。本包只在 Host 一侧使用，runtime 经通道检索记忆（见 agent-runtime 的[通道](agent-runtime.md#通道)）。

## 两种范围

| 范围 | 存什么 | 用途 |
|---|---|---|
| Project | 架构决策、项目约束、测试命令、失败过的尝试及原因 | 在同一项目的不同 session 之间复用 |
| User | 个人偏好、协作习惯 | 只属于这个用户，可以跨项目使用 |

范围决定"谁能用、在哪里用"；内容类型（事实、偏好、决策、经验）和保存期限是另外的属性，两种范围共用一套记录格式和接口。当前 session 的内容不另存一份"session 记忆"：继续当前任务、压缩上下文和恢复都直接用 session 记录。

## 模块

```text
memory/
  core/        记录格式：范围、来源、是否仍有效、纠正和删除规则
  long-term/   长期记忆的提取、整理和检索
  storage/     本地存储和索引（实现可替换），以及数据迁移和导出
  sdk/         对外接口：记录、检索、纠正、遗忘、导出
```

## 要点

- session 记录里的内容经过筛选和确认才能成为 project 或 user 记忆（由谁筛选和确认、什么时候触发，见下文[写入](#写入)）。session 记录由 Host 从 session-store 读出后交给本包，本包不依赖 session-store。每条记忆记下内容来自用户本人的表述，还是来自文件、网页、工具输出等不可信内容；不可信内容不能自动成为 user 记忆，否则一个仓库里的注入内容会随 user 记忆进入别的项目。
- 每条长期记忆都记下来源：哪次会话、哪些文件、哪个 commit。相关代码变化后要重新确认。
- Project 记忆按 Host 判断的项目身份隔离（见 agent-host 的[项目身份](agent-host.md#项目身份)），不采信仓库内容自己声明的身份，否则一个陌生仓库可以冒充别的项目，读到它的记忆。
- 范围要落实到实际的存储空间，读、写、改、删都检查范围，不能只在查询时按附加字段过滤：Mem0 只在查询时按 project 过滤，抽取步骤就会看到同一用户别的项目的记忆。
- "不再使用"、"标记过期"和"彻底删除"是三种不同操作。彻底删除要覆盖记忆本身、它的历史版本、摘要、索引、缓存，以及本项目产生的备份和导出；重建索引时不能把已删除的内容找回来。用户要求忘记的内容如果也出现在 session 记录里，由 Host 同时让 session-store 按事件脱敏（见 session-store 的[要点](session-store.md#要点)）。
- 不内置默认的存储位置，所有位置都由调用方显式传入，并通过重启测试。
- 提取和整理要调用模型时，由调用方传入发起调用的函数，请求同样经过 Host 的模型代理。
- 疑似密钥、令牌的内容不写入长期记忆，检测函数由调用方传入（Host 的 `redaction/`，见 agent-host 的[模块](agent-host.md#模块)）。
- 多个 worker，或同一项目不同 worktree 上同时运行的 Host，同时更新同一条记忆时要能发现冲突，不能悄悄覆盖。
- 只返回带来源的结果；要不要放进模型上下文、放多少，由 runtime 决定。放进上下文时标明来源，和用户当前的明确要求冲突时以当前要求为准。

## 记录格式

每条记忆包含类型（事实、偏好、决策、经验）、一行标题、简短正文、状态（待确认、生效、不再使用、已过期）、内容来自用户本人还是不可信内容、来源（session、事件、文件路径和行号及内容哈希、commit）、版本号、确认时间和最近使用时间；范围由所在的数据库文件决定（见下文[存储](#存储)）。P3 不建向量和全文索引，不设按时间到期，不做全局整理，等评测显示有收益再加。

## 写入

写入有三个入口：用户在 CLI 里直接添加；模型在任务中调用 `memory_propose` 提议；Host 打开同一项目的新 session 时，从空闲的旧 session 记录里后台提取。

- 除了用户在 CLI 里亲手输入的内容，其余都只生成"待确认"的候选：由模型筛选，由用户在 Host 一侧确认，project 和 user 两种范围相同。交互模式在 task 结束时列出候选，用户可以确认、修改后确认或拒绝；非交互运行时候选保持待确认，不自动生效（照 Gemini CLI 的 Auto Memory 收件箱）。
- `memory_propose` 是 runtime 的内置工具，P3 启用，只给主 agent（见 agent-runtime 的[工具集、系统指令和模型切换](agent-runtime.md#工具集系统指令和模型切换)；照 Copilot CLI 只让 root agent 用 `store_memory`）。
- project 记忆也要确认：候选是模型综合整个上下文写出的，Host 无法可靠判断它只来自用户，写进记忆后会出现在之后每个 session 的开头；不经批准的记忆写入已有被注入内容利用、持续外泄数据的先例（Windsurf 的 `create_memory`）。确认放在 Host 的 CLI 里，沙盒内的检查不作为安全保证。
- 不选"只记用户明确要求的内容"：它会漏掉测试命令、失败尝试这类 project 记忆的主要内容；这种做法保留为评测里的一种写入策略。
- 后台提取：处理关闭后空闲 6 小时以上、最近 10 天内、还没提取过的 session，每次最多 2 个（取 Codex rust-v0.167.0 源码的默认值，它的文档写的 16 个和 30 天与源码不符）。提取作为来源标为"记忆提取"的 task 的一个 run 运行，预算固定为每次 1 美元、20 次请求，事件照常记录。
- 评测比较写入方式时，由 evaluation 通过 Host SDK 按脚本确认候选，产品不加"自动确认"开关。
- 入库时中和不可见字符和伪装成系统标记的内容（照 Claude Code 2.1.284），并用 `redaction/` 拒绝含密钥的候选。

## 检索

自动放进上下文的只有一份短索引，正文由模型按需取得。

- session 开始时，Host 把当前 user 范围和 project 范围内生效记忆的索引作为启动配置之一交给 runtime（见 agent-runtime 的[从 Host 得到的配置](agent-runtime.md#从-host-得到的配置)）：每条只有标题、类型、来源和"引用已改动"标记（由 runtime 在沙盒里核对后加上，见下文[查看、纠正和删除](#查看纠正和删除)），总长不超过 2,500 token（照 Codex）。runtime 把它放进会话开始的上下文消息，排在规则文件和 skills 列表之后，注明"来自过去的会话，可能过期，用前按引用核实"，不放进系统指令（见 api 的[追加指令的来源](api.md#追加指令的来源)）。
- 正文由模型调用 `memory_search`、`memory_read` 按需取得，不在每个 task 开始时自动注入：选错的记忆有害，VibeMemBench 中统一注入检索结果的 12 组"系统 × 模型"组合有 11 组不超过无记忆。这两个工具和 `memory_propose` 一样是 runtime 的内置工具，P3 启用，只给主 agent（见 agent-runtime 的[工具集、系统指令和模型切换](agent-runtime.md#工具集系统指令和模型切换)）。
- session 中新确认、停用或删除的记忆，在下一个 task 开始时以"记忆更新"追加。
- 不采用 Anthropic 的 `memory_20250818` 工具：它只属于 `anthropic.messages`，API 还会在系统提示里自动加一句"先查看记忆目录"。

## 和规则文件的关系

project 记忆不写进规则文件（`AGENTS.md` 等，见 agent-runtime 的[工具集、系统指令和模型切换](agent-runtime.md#工具集系统指令和模型切换)），memory 包和 Host 都不自动修改规则文件。

- 规则文件是仓库内容，随版本库共享给团队和其他 agent；记忆属于本机和个人，还可能含不可信来源，自动写入等于把模型输出推进团队共享的指令，也是对用户仓库的一次写入。用户想固化某条记忆时，让 agent 用普通编辑工具修改规则文件，照常经过 Permission，再把这条记忆设为"不再使用"。
- 冲突时以用户当前的明确要求为准，其次是规则文件，最后是记忆。规则文件在会话开始时读取，代表项目当前的约定，和它冲突的 project 记忆多半已经过期，runtime 在索引里标"可能过期"并提示用户处理；user 记忆和某个项目的规则文件冲突时，在这个项目里按规则文件，在其他项目照常使用。这里的优先级只管行为约定，两者都不能改变权限。
- 提取记忆时去掉规则文件和 skill 的内容（照 Codex），也不保存规则文件已经写明的内容，从源头上减少重复和冲突。

## 查看、纠正和删除

CLI 的 `/memory`（见 agent-host 的 [CLI](agent-host.md#cli)）和 Host SDK 提供同一组操作：列出、查看正文和来源、确认或拒绝候选、直接添加、纠正、"不再使用"、"标记过期"和彻底删除。

- 纠正生成新版本，旧版本保留到彻底删除为止，可以回滚，纠正后的内容记为来自用户。"不再使用"的记忆不再返回给 runtime，可以恢复；"标记过期"表示内容曾经成立、现在不成立，不进索引也不返回，纠正后重新生效；彻底删除清除记忆、全部版本、来源和索引。
- 列表明确显示每条的状态，不把隐藏当作删除。用户不直接编辑存储文件，所有修改都经过命令，范围检查、来源记录和冲突检测才能生效。
- 每条记忆记下引用文件的内容哈希和 commit。Host 不运行 git，也不读仓库源文件：写入时，候选里引用文件的哈希由 runtime 在沙盒里计算并随 `memory_propose` 提交，commit 由 Host 读 git 目录里的 `HEAD` 得到，用户在 CLI 直接添加的记忆不带文件哈希；session 开始时，runtime 在 agent 沙盒里按 Host 给出的路径和期望哈希核对，不符的在索引上标"引用已改动"，由模型按引用核实，纠正还是标记过期由用户决定（照 Copilot 使用前按引用核实的做法）。
- 不设按时间到期（Copilot 的 90 天针对的是不经确认就写入的记忆）；记下最近使用时间，留给评测判断是否需要。
- 被删除的 session 作为来源时，用户要求忘记就连记忆一起删，到期清理只把来源标为已过期（见 session-store 的[保存期限](session-store.md#保存期限)）。

## 存储

和 session-store 用同一个 SQLite 绑定（`node:sqlite`，见 session-store 的[存储格式](session-store.md#存储格式)），但表结构和数据库文件分开：user 范围一个文件 `data/user/memory.sqlite`，每个 project 一个文件 `data/projects/<project_id>/memory.sqlite`（见 agent-host 的[目录位置](agent-host.md#目录位置)），路径由 Host 传入；`user_id` 由 Host 生成（见 agent-host 的[标识](agent-host.md#标识)）。

- 按范围分文件后查询不可能跨范围，删除一个项目的全部记忆就是删除它的文件，评测的无记忆组也不打开任何记忆库。
- 连接时显式设 WAL、`busy_timeout=5000`、`secure_delete=ON` 和 `synchronous=FULL`。更新带版本号，`UPDATE … WHERE id = ? AND version = ?` 没有改到行就报冲突，不悄悄覆盖。
- 不以 Markdown 文件为本体：要记来源、状态和版本，彻底删除时也不能留下副本；导出时再生成 Markdown 或 JSONL。
- 检索逐条做子串匹配，不建索引：向量索引要额外调用嵌入模型；实测 FTS5 的 `unicode61` 分词搜不到中文子串、`trigram` 搜不到两个字的词，而且用了 FTS5 时彻底删除还要对它执行 `optimize`，否则词项留在索引里。
- APFS、SSD 和 Time Machine 上覆盖写不等于物理擦除，文档要写明彻底删除覆盖到哪一层。

## 评测

记忆的价值要和无记忆组对比（见 evaluation 的 [Memory 评测](evaluation.md#memory-评测)）。

- evaluation 的五组对比里，注入等长无关记忆的对照组用来区分"多了上下文"和"记忆本身"的影响；诊断组（由 evaluation 直接给出正确证据的那一组）单独报告。完整 memory 组内部再比较写入策略（只记用户明确要求的、加上模型提议、再加上后台提取）和检索方式（只给索引、只给工具、两者都给、自动注入前几条正文）。检索方式靠 runtime 的 context 里一个只能由 SDK 调用方传入的"记忆注入方式"选项（索引、工具、自动注入前 N 条正文）切换，CLI 不暴露它。
- 同一道题配对比较，每组至少运行 3 次，以题为单位做 bootstrap 求置信区间，按无记忆时的通过次数分层，并按模型分开报告：无记忆时已稳定通过的题，记忆只会有害；同一条记录对弱模型有益、对强模型有害，只看平均会掩盖这些差异。
- 用检索和提议事件把失败归到五类：没写入、没确认、没检索到、检索到但没用、误用过期记忆；同时统计提取的 token、每个 task 的候选数和确认次数、每个 session 的索引 token。
- 安全测试在仓库文件、网页和工具输出里放注入指令，检查没有确认的内容不会生效，user 记忆不会从不可信内容自动产生，冒充的项目身份读不到别的项目的记忆，彻底删除后数据库文件里扫描不到原文。
- 题目要真正依赖记忆：题目之间补丁相似度很低的题集（如 SWE-Bench-CL）得不出结论；Letta 的 FrontierMemory 用过去的执行轨迹写成记忆再解题，可作参照。
- 现成系统不作为 P3 的对照组；P4 把 Mem0 作为外部系统对照组加入，单独报告：现有证据显示它低于无记忆。
- 用 Mem0 时选 Python 版，在单独的进程里运行：TS 版的必需 peer 依赖 `better-sqlite3` 带 install 脚本，evaluation 也要按 SDK 标准来做。每次运行设 `MEM0_TELEMETRY=false`（它同时关掉从 `raw.githubusercontent.com` 拉取提示配置），用临时 HOME 和单独的 `MEM0_DIR`，并显式设置 `vector_store.config.path` 和 `history_db_path`：历史库默认在 `~/.mem0/history.db`、导入时还写 `~/.mem0/config.json`、向量库固定在 `/tmp/qdrant`，不受 `MEM0_DIR` 控制，题目之间会共用，并发运行时还会因为目录被独占锁定而报错；它写入时把最近 10 条消息放进抽取步骤，不分开的话状态会在题目之间延续。它默认用 `gpt-5-mini` 和 `text-embedding-3-small`，模型和嵌入请求经 `openai_base_url` 指向记录用量的代理，费用计入对照组。

## 可以借鉴的设计

| 项目 | 可借鉴的做法 |
|---|---|
| Engram（Gentleman-Programming/engram） | SQLite 加全文检索的轻量本地存储，按主题更新同一条记忆，会话交接摘要 |
| Hindsight（vectorize-io/hindsight） | 保存、召回、反思三步处理，保留证据的观察记录和时间推理 |
| OpenViking（volcengine/OpenViking） | 资源、用户记忆、会话分层组织，会话提交后再异步提取记忆；AGPL-3.0，只参考设计 |
| tigerless-labs/agent-memory | 记忆的有效时间区间和来源记录 |
| memsearch（zilliztech/memsearch）、akitaonrails/ai-memory | 以 Markdown 文件为内容本体、索引随时可重建，ai-memory 另有跨项目的个人档案和交接 |
| Mem0 | 新增、检索、更新、删除、历史这组基本接口；范围隔离、删除和持久化上的不足作为反面参考 |
