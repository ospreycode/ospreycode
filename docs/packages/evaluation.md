# `evaluation`：评测

## 模块

```text
evaluation/
  adapters/     通过公开接口接入各包
  suites/       agent 能力评测场景，以及 sandbox 专项评测场景
  benchmarks/   公开编码和记忆 benchmark 的接入，固定数据版本
  runners/      准备环境、隔离、并发和清理
  traces/       解析 session-store 里的执行记录，定位问题出在哪一步
  reports/      成功率、成本、耗时、失败分类
```

上面是 `src/` 里的模块。包根目录另有一个 `benchmarks/`，放随评测代码提交的数据和要进任务容器的文件：SWE-bench Pro V2 的题目清单、编码能力评测的权限规则文件、Pier 的 agent 适配和它调用的脚本。它们不是 TypeScript 模块，不经构建，源码和构建结果按同一个相对位置找到它们。

## 两类评测

- **Agent 能力评测**：覆盖 tools、loop、memory、扩展、CLI 和端到端任务。不启用系统隔离，评测环境由容器或虚拟机隔离。权限检查按评测内容设置：编码能力评测用预设的放行规则，不拦截；批准、拒绝和取消流程的评测照常运行 Permission（见[评测时的权限配置](#评测时的权限配置)）。
- **Sandbox 专项评测**：检查权限判断是否正确、系统限制能否被绕过、正常的开发操作会不会被误拦。在每个支持的平台上启用真实沙盒，以固定的权限请求和命令为输入。另用一小组编码题在开启沙盒时完整运行，和关闭沙盒的结果对比，衡量沙盒对完成率、批准次数和耗时的影响：产品默认开启沙盒，只看关闭沙盒的结果会高估实际效果。

测试和评测默认用便宜的真实模型联网运行，报告注明所用模型；重要结论需要时再用正式使用的模型复核。模型服务报错、超时、在指定时刻取消这类真实模型难以稳定触发的情况，用 `api` 包里按脚本返回结果的模型模拟。

各包自己的单元测试和集成测试放在各自的 `test/` 里；evaluation 负责跨包的接口回归、版本对比和完整系统实验，调用真实的工具和 loop，不另写一套应付考试的实现。

接口：跨包的回归和 Host 级的评测直接调用 Host 的 `sdk/`；Pier 这类在任务容器里运行 agent 的 benchmark，通过 CLI 的非交互模式和它的 JSON 事件流接入（见 agent-host 的 [CLI](agent-host.md#cli)）。

## 评测要求

| 对象 | 要回答的问题 | 怎么检查 |
|---|---|---|
| Tools | 动作是否正确，错误和副作用是否清楚 | 输入输出、文件结果、退出码、超时和取消、输出超长、编辑时文件已被别人改过 |
| Loop | 调度、预算、停止和恢复是否合理 | 用真实模型跑任务并检查执行记录；取消和中断后对话记录完整；模型报错、超时用脚本模拟 |
| api | 各协议的转换是否正确、有没有丢信息 | 每种协议用真实模型跑通文本、流式、工具调用、推理内容、取消和用量；同一段对话在协议之间往返转换；各家的错误归入正确的类别 |
| Session 记录 | 记录是否完整可靠，恢复和回退能否依靠它 | 崩溃后读回的事件不丢、不重复、顺序正确；同一 session 的第二个写入者被拒绝；不同 project 的记录互相读不到；删除覆盖所有副本，重建索引后找不回；格式迁移前后读到的内容一致 |
| 通道 | Host 能否挡住沙盒内发来的越权请求 | 伪造的标识、不在接口里的操作、格式不对的消息都被拒绝；被攻破的 runtime 绕不过权限检查、读不到别的 session 的记录 |
| Memory | 是否记对、找对、及时过期、范围不串 | 范围隔离、纠正和删除、重启后恢复；不可信内容不升级成 user 记忆；冒充的项目身份读不到别的项目的记忆（见 [Memory 评测](#memory-评测)） |
| 扩展 | MCP、Skills、插件是否按规范正确接入；hooks 是否按设计工作 | 先单独测 `skills`、`mcp`、`agent-plugins` 对规范的实现，再经 Host 和 runtime 测整体接入；插件加载按 Agent Plugins 规范正文第 1 到 11 节测试（官方的 agent-plugins-conformance 只作参考，它没有检查的 `PLUGIN_DATA` 在更新后是否保留、清单无效时是否拒绝整个插件、经越界链接读取清单和 skill 要自己测）；用其他客户端在用的 MCP server、skills 和插件做兼容测试；hooks 的继续、阻止、补充信息和超时；仓库自带扩展未经确认不启用，内容改变后重新确认；扩展的工具不能覆盖内置工具 |
| CLI 和 Host | 用户能否可靠地控制任务 | 交互批准、取消、各审批策略在交互和非交互运行时的处理、非交互模式的输出格式和退出码、退出后恢复会话、同一工作区不能同时打开两个 session；steering 在工具调用结束后、下一次模型请求前插入，follow-up 只在 task 正常完成后逐条开始，取消和失败后列表暂停；后台命令跨 task 保留、结束时唤醒 session、session 结束时停止、恢复时报告丢失；回退和分叉后发给模型的历史只有当前路径，文件按选择还原 |
| 整体 | 能否完成真实编码任务，成本是否合理 | 隐藏测试、约束是否满足、总费用和耗时、失败原因 |
| Sandbox（专项） | 权限判断是否正确；系统限制能否被绕过；会不会误拦正常开发操作 | 用固定的命令集核对规则匹配和内置危险命令判断，统计多问（不必要的询问）和漏问（该问的没问）；按沙盒模式和审批策略的组合核对执行、询问和拒绝；越界申请只按批准的权限执行，不在沙盒外运行；未放行的域名按审批策略询问或拒绝；越界读写、写入受保护路径、未批准的网络访问、读取凭据（密钥文件、钥匙串、环境变量）、访问 Unix socket 和本机端口、子进程逃逸、session 结束后残留进程；git、包管理器、编译、测试命令和本地测试服务在沙盒内的运行情况和额外耗时；开关沙盒时编码题结果的对比 |

除 Sandbox 专项外，各项都在不启用系统隔离的评测环境中运行。

## Memory 评测

P3 起。Memory 测连续多会话的编码场景：学到测试命令后再次使用；代码改了以后纠正旧记忆；在另一个项目中使用个人偏好；恢复没做完的任务；用户要求忘记后不再受影响；长期偏好和用户当前的明确要求冲突时，遵守当前要求；历史方案和当前问题表面相似、根因不同时，重新验证而不是照搬。

- **对比组**：P3 对比五组：无记忆、直接提供历史或摘要、只检索、完整 memory、注入等长无关记忆的对照组（区分"多了上下文"和"记忆本身"的影响）。各组使用相同的模型、权限和预算，后台提取记忆的开销也计入。完整 memory 组内部的比较见 memory 的[评测](memory.md#评测)。
  - 一道题由前面的几个学习会话和最后一个检验会话组成：每个会话是一个新的 session、只做一个 task，同一道题的各个会话共用一个临时 HOME 和工作区，只有检验会话用隐藏检查判定。各组学习会话的输入相同，只差记忆。
  - 无记忆：所有会话都关掉长期记忆。
  - 直接提供历史：关掉长期记忆，把学习会话的文字记录（用户的输入、模型的回复、工具调用和结果，每条截到 4,000 个字符）放在检验会话的输入前面，超过 100,000 个字符时留末尾。不让模型先写摘要：摘要写得好不好是另一个变量。
  - 只检索：关掉长期记忆，把同一份记录按条切开，用检验会话的输入作查询，按 `memory_search` 的词匹配取前 5 条放在输入前面。它和完整 memory 的差别只在有没有提炼和确认。
  - 完整 memory：用产品的默认选项（模型提议加后台提取，索引加检索工具）。学习会话的 task 结束后按脚本确认全部候选；下一个会话之前，单独打开一个不做 task 的 session，对上一个会话"立即提取"，再确认全部候选。提取不放在下一个会话里做：会话中途确认的记忆以"记忆更新"的形式出现在输入前面，放在单独的 session 里，检验会话开头的索引才是完整的。
  - 等长无关记忆：学习会话关掉长期记忆；检验会话开着，之前同样单独打开一个 session 添加和题目无关的记忆，条数和每条的字符数取自同一道题同一次运行里完整 memory 组生效的记忆，内容来自一张固定的无关记忆表。这样两组的记忆出现在同样的位置。
- 另有两组单独报告：由 evaluation 直接给出正确证据的诊断组，用来判断失败出在写入、检索还是使用；P4 加入的 Mem0 外部系统对照组。
- **统计**：同一道题配对比较，每组至少运行 3 次，以题为单位做 bootstrap 求置信区间，按无记忆时的通过次数分层，并按模型分开报告：无记忆时已稳定通过的题，记忆只会有害；同一条记录对弱模型有益、对强模型有害，只看平均会掩盖这些差异。
  - 每道题每组的通过率减去无记忆组的，以题为单位重抽样 10,000 次（固定种子），取 2.5% 和 97.5% 分位。分层是无记忆时从不通过、有时通过、每次通过三层。
  - 每组不足 3 次时报告照常给出数字，并注明不能据此下结论。
- 除成功率外，统计重复的工具调用、重复读文件、重复的失败尝试和误用过期记忆的次数；没有记忆和已有记忆两种状态分开报告：学习会话是前一种，检验会话是后一种，会话之间整理记忆的 session 另算一项。
  - 这几项只数检验会话里的调用：名字和参数与同一道题里之前出现过的调用相同，算重复的工具调用；`read` 读的是学习会话读过的文件，算重复读文件；和之前一次没成功的调用相同、这次也没成功，算重复的失败尝试；记忆工具的调用不算在这三项里。误用过期记忆由题目自己的检查给出（比如执行了已经作废的命令）。
- **失败归类**（见 memory 的[评测](memory.md#评测)）：完整 memory 组没通过的运行，按题目给出的"这段文字里有没有解题要用的信息"依次判断：题目的检查报告了误用过期记忆；没有一条记忆或候选含这个信息（没写入）；含它的都没有生效（没确认）；检验会话的 `memory.retrieved` 里没有它（没检索到）；其余是检索到但没用。
- **题目**要真正依赖记忆：题目之间补丁相似度很低的题集（如 SWE-Bench-CL）得不出结论。
- **Mem0 对照组**（P4）：用 Python 版，在单独的进程里运行（TS 版的必需依赖带 install 脚本）。每次运行设 `MEM0_TELEMETRY=false`，用临时 HOME 和单独的 `MEM0_DIR`，并显式设置 `vector_store.config.path` 和 `history_db_path`：它的历史库、配置和向量库默认放在 `MEM0_DIR` 之外的固定位置，题目之间会共用，并发运行时还会因为目录被锁定而报错。它默认用 `gpt-5-mini` 和 `text-embedding-3-small`，模型和嵌入请求经 `openai_base_url` 指向记录用量的代理，费用计入对照组。

## 防止刷分

- 每道 benchmark 题从干净状态开始，记忆不在题目之间延续；连续学习实验事先规定允许延续哪些历史。
- 标准答案、隐藏测试和未来的会话只放在 evaluation 一侧，agent 能读到的文件里没有它们，包括题目仓库的 git 历史。
- agent 只能访问模型服务，不能联网查到题目的上游修复。模型服务自带的联网搜索、网页读取等服务端工具也关闭：这些请求由模型服务发出，不受评测环境的网络限制。不传这些工具还不够：OpenAI 的 Chat Completions 搜索模型每次回答前都会搜索，排除在外；Anthropic 的 web search 和 web fetch 由组织管理员在 Console 里对整个组织关闭，评测用的密钥放在关闭了这两项的组织里。
- 开发用的题和最终检验用的题按仓库或任务类型分开，不在同一批题上反复调。
- 不写针对具体题目的规则，改进落在通用的工具、上下文、记忆和恢复设计上。

## 报告

报告给出：成功率；全部任务（不只是成功的任务）的成本和耗时；超预算和环境故障的次数；每道题重复运行的结果波动范围。厂商公布的分数只作参考。

- **环境故障**指 agent 没有运行（开始前的检查没过、镜像或安装出错、CLI 的参数或配置有误），或者补丁没能在干净的镜像里评分。它不计入成功率的分母，在报告里逐次列出原因：这些运行说明不了 agent 的能力。清单里有、结果里没有的运行也逐次列出。
- 评分的测试超时算不通过，不算环境故障：否则让测试卡住的补丁会被排除在成功率之外。模型服务出错导致 task 失败的运行也照常评分。
- 波动范围按运行给出：每道题的第 N 次运行合在一起算一个成功率，报告各次的成功率和它们的范围，以及每次都通过、每次都不通过、有时通过的题数。

报告记录实验条件：模型和所用协议、提示和配置、被测的 commit、是否启用沙盒及所用后端、记忆快照和操作系统。模型或环境无法固定时注明，不把环境差异算成架构改进。

## 首批 benchmark

- **P1 的编码题**取 SWE-bench Pro V2（642 题，Harbor 任务格式）中的 60 道：排除 51 道 `hard` 题（便宜模型几乎全错，只增加费用）后按仓库划分，Go、Python、JavaScript 各选一个仓库只出保留题，共抽 20 道；其余仓库按语言分层抽 40 道作开发题。题目清单和抽样种子放在 `evaluation/benchmarks/swe-bench-pro-v2`，按 `scaleapi/SWE-bench_Pro-os` 的 commit 和镜像 digest 固定，每道题跑 3 次。开发题随时可跑，保留题只在阶段验收和大的架构改动合并前运行，每次都写进报告。
  - 选 V2：每道题都经过"参考补丁能过、空补丁会失败"的检查，官方流程也只放行模型服务、在干净镜像上重新评分。不用 SWE-bench Verified：已知污染和坏题。题目沿用上游仓库各自的许可证，评测框架是 MIT，镜像只有 linux/amd64。
  - 抽样：仓库和题目的先后按 `sha256("<种子>:<名字>")` 排，种子是 `osprey-p1`，同样的输入每次得到同一批题。每种语言里排在最前的仓库只出保留题（Go 的 `future-architect/vuls`、Python 的 `ansible/ansible`、JavaScript 的 `NodeBB/NodeBB`），20 道按 7、7、6 分给它们；开发题在其余仓库里按各语言的题数比例分配（Go 17、Python 13、TypeScript 10）。
  - 固定：题目从 GitHub 仓库的 `v2/tasks` 读取，不经过 Hugging Face 的数据集，所以不按 Hugging Face 的 revision 固定。镜像的标签可以被重新推送，清单记下每道题镜像的 digest，准备数据集时把题目里的镜像引用换成 digest；检出不在固定的 commit 上就不准备。
  - 两遍运行：Pier 0.3.1 不能原样加载 V2 的 `task.toml`。题目让 agent 不联网、评分联网（少数 Go 题评分时要下载模块），Pier 在 agent 用过的容器里评分，中途换不了网络策略，加载时就报错；它分开评分的模式只把 `/logs/artifacts` 带过去，题目的测试用不上。所以照上游的官方流程分两遍，准备数据集时把每道题写成两份：第一份去掉评分的网络设置，用 `--disable-verification` 只运行 agent、导出补丁；第二份把 agent 阶段的网络放开，由一个不调用模型的重放 agent 把补丁打到干净的镜像上，再跑题目原样的测试。只有第二遍的结果算数：agent 用过的容器可能被改过测试工具、留下进程。补丁在干净的镜像上打不上算环境故障。
  - 每道题的 3 次运行是 3 对单独的 job，每个 job 里一道题只运行一次：各次运行的成功率才能分开算。
- **P4 的主 benchmark** 用 DeepSWE v1.1（`datacurve-ai/deep-swe`）：113 道从零编写的题，污染风险最低；单题超时 10800 秒，不适合 P1 频繁迭代。SWE-bench Pro V2 的保留题继续用作回归。
  - 版本：仓库没有 v1.1 的标签，固定在 commit `0b9fabb`。题目的镜像都基于 `mars-base:latest`，评测按 digest 固定。
  - 许可证：Apache-2.0 只覆盖 Datacurve 自己的内容，上游项目的许可证不变（都是宽松许可）。
  - 网络：agent 通过 `network_allowlist()` 声明放行的域名；题目的 `task.toml` 写的是 `network_mode = "no-network"`，适配里要放行模型服务的域名。
  - 评分：从 agent 结束时提交的 commit 中提取补丁（`git diff --binary <base_commit> HEAD`），在单独的环境中评分，没有提交的改动不计分。
- 不用 Terminal-Bench 作主 benchmark：偏科研和前沿工程，部分题要 GPU、超时 8 小时。
- **记忆评测**以自建的连续多会话编码场景为主，参照 VibeMemBench 和 MemDev-Bench：后面会话的题依赖前面会话里推不出来的信息，用隐藏测试判定。Letta 的 FrontierMemory（15 道题，CC-BY-4.0，需申请）是候选；LongMemEval（MIT）只单独测 `memory` 的检索。不用 LoCoMo：CC BY-NC 4.0 不允许商用。不用 LongMemEval-V2（`xiaowu0162/LongMemEval-V2`）：不运行 agent、不是编码题，还需要图片输入。
- **运行器**：两个编码 benchmark 都用 Pier（`datacurve-ai/pier`，Apache-2.0，PyPI 包名 `datacurve-pier`），固定 0.3.1。另加一个必须失败的探测请求，确认网络确实被限制：0.3.0 及更早的版本会悄悄忽略 `network_mode`。
- **Pier 的 agent 适配**是一个 Python 类，继承 `BaseInstalledAgent`，实现安装步骤（docker 环境在构建镜像时就执行，所以 Node 要装进镜像）、运行命令、运行后上报轨迹和 token 用量，以及 `network_allowlist()`；运行时用 `--agent-import-path` 指定。
  - 安装：Node 和 CLI 装在单独的目录里，不加进 `PATH`，CLI 经一个写明 Node 路径的包装脚本启动：题目的测试和 agent 运行的命令要用镜像自带的 Node。CLI 用 `npm install --ignore-scripts` 安装，装哪些包由运行评测的人给出（发布后的版本号，或各个包的 tarball 地址）。
  - 运行：适配只准备参数，检查环境、运行 CLI 和导出补丁都在一个 bash 脚本里（`benchmarks/pier/run-agent.sh`）。本地夹具的测试直接运行这个脚本，容器里走的是同一段流程。参数全部经环境变量给出，缺一个就报错。
  - 开始前的检查，任何一项没过都不运行 agent，记为环境故障：隐藏测试和参考答案的目录不存在；仓库的对象库里没有上游修复的 commit（题目 id 里带着它）；每个引用（分支、标签、stash）都在 `HEAD` 的历史里；必须失败的探测请求按 agent 的代理设置和绕过代理各发一次，都访问不到。
  - 补丁：SWE-bench Pro V2 不要求提交。脚本在 agent 开始前后各给整个工作区建一个 tree（用单独的 index 文件，不动仓库自己的 index），补丁是两者之差，提交过的、没提交的和新建的文件都在里面，仓库开始时不干净也不影响。
  - 轨迹就是 CLI 的 JSON 事件流，原样存在这次运行的日志目录里，不另转格式；token 用量和费用取自 `session.ended`，被拒的工具调用从 `tool_call.completed` 统计。
  - docker 环境的出站流量经过要认证的 Squid 代理，agent 只拿到带凭据的 `HTTPS_PROXY`，CLI 入口据此开启代理（见 overview 的[语言和运行环境](../overview.md#语言和运行环境)）。
  - 题目的 agent 时限到了，Pier 直接结束命令，之后的改动和补丁都拿不到，所以运行评测时给 CLI 的时限要比题目的更早，留出收尾和导出补丁的时间（V2 的题目是 3000 秒，评测用 2700 秒）；CLI 到时限后一分钟还没退出，脚本结束它再导出补丁。DeepSWE 的每道题还要求 agent 在新分支上工作、结束时提交全部改动，只有已提交的改动计分，它的适配在最后提交。
  - API 密钥通过容器的环境变量传入，Host 用 `--credential-env` 读取后不再传给 agent 进程。评测不启用沙盒，agent 仍能从 `/proc/<Host 的 pid>/environ` 读到它（见 sandbox 的[分层](sandbox.md#分层)），所以评测用的密钥只用于评测，并设好额度上限。

## 评测时的权限配置

编码能力评测，以及 tools、loop、memory、扩展和端到端评测，用启动参数指定 `danger-full-access` 和 `never`，再用 `--rules` 传入随评测代码提交的权限规则文件。编码能力等评测的权限规则文件只含 `pattern = ["rm"]`、`decision = "allow"` 一条；扩展评测（MCP、skills、插件、hooks 的整体接入）另加测试用 server 和工具的 `allow` 规则：`never` 下没有 `allow` 规则的 MCP 工具调用会被直接拒绝。

- `danger-full-access` 就是"不启用系统隔离"，是产品本来就有的模式，不加评测专用的开关。
- `rm` 的 `allow` 规则盖过危险命令判断，`rm -rf build/` 这类常见命令才不会在 `never` 下被拒；带重定向和变量的写法（如 `rm -rf build/ 2>/dev/null`）一样放行。这条规则经启动参数传入、不在被测仓库里，符合"仓库配置只能收紧"。
- 内置 `forbidden` 照常生效：它只拦提权、删除关键路径、写磁盘设备等，正常解题很少碰到，关掉它就要在产品代码里加评测分支。被拦的次数照实报告；某个 benchmark 经常撞上，说明范围要调整，而不是在评测里绕开。容器里以 root 运行时模型常写 `sudo apt-get install`，拒绝信息提示去掉 `sudo` 再试，并单独统计这一类。
- 批准、拒绝和取消流程的评测用 `danger-full-access` 加 `on-request` 或 `granular`，由测试用的 `prompt` 规则、危险命令判断、MCP 工具调用和权限申请工具触发询问，审批方按脚本经 `sdk/` 应答；越界申请依赖真实沙盒，放在 sandbox 专项评测里。
- 每个 run 的上限由运行评测的人显式给出全部三项（见 agent-host 的[预算](agent-host.md#预算)）。超出后是否追加额度的询问不交给场景的脚本，运行器一律拒绝，task 以 `budget_exceeded` 结束并计入超预算的次数：脚本批准了它，上限就不起作用。
- 沙盒对比实验两组都用 `never` 和同一份权限规则文件，另加预先放行包仓库的域名规则，只差沙盒模式。
- 报告写明沙盒模式、审批策略、权限规则文件全文和 `sandbox` 包的版本，并按原因统计被拒次数：内置 `forbidden`、危险命令判断、`prompt` 规则、越界申请和 MCP。后四项取自被拒结果的 `categories`（见 agent-host 的[工具调用的处理](agent-host.md#工具调用的处理)），一次调用要询问几类就各计一次。
- 和其他 agent 对比时写明对方的配置：运行器给对方的"跳过权限"参数并不等于不拦截，例如 Codex 仍拒绝强制删除，Claude Code 仍拒绝删除关键路径。

## Sandbox 专项评测的组成

分两层，都不需要真实模型和网络，输入逐次相同：

- **权限判断**：固定的命令和请求直接交给 `sandbox` 包的判断函数，逐条核对是执行、询问还是拒绝，覆盖固定命令集（规则匹配、内置 `forbidden`、危险命令判断）以及沙盒模式和审批策略的各种组合。该直接执行的被询问或拒绝记为多问，该询问或拒绝的直接执行了记为漏问。
- **真实沙盒里的用例**：经 Host 的 `sdk/` 打开 session，由 `api` 包里按脚本返回结果的模型依次发出固定的工具调用，按结构化的结果检查。固定的输入只能由脚本给出，真实模型写不出逐次相同的命令。用例分逃逸探测（越界读写、受保护的路径、网络、凭据、本机服务、子进程和残留进程、越界申请）、命名权限配置和正常的开发操作（git、包管理器、编译、测试、本地测试服务、构建工具的缓存）。
  - 对照：预期被沙盒拦住的调用，在 `danger-full-access` 下原样再运行一遍，应当成功。不启用沙盒时也做不成的调用，失败说明不了沙盒拦住了它。要联网的和会留下进程的调用不做对照。
  - 额外耗时：量耗时的用例把同样的调用在 `danger-full-access` 下再运行一遍，报告两边的耗时。
  - 网络用例不产生真实的流量：只看 Host 的代理放不放行，用的是会被拒绝的请求和解析不了的域名。
  - 只在某个平台上成立的用例标明平台，其余平台上跳过并写进报告；沙盒后端报告不支持时记为"后端不支持"，不算通过。

报告按防护范围列出每个用例通过、不通过、跳过还是后端不支持，给出多问和漏问的条数、各用例的额外耗时，以及平台、内核和 runner 镜像的版本。开关沙盒的编码题对比在 P4 做（见下一节）。

## Sandbox 专项评测的运行环境

固定命令集和逃逸探测在 GitHub 托管的虚拟机上直接运行，不放进普通的 Docker 容器。

- Linux 固定用 `ubuntu-24.04` 和 `ubuntu-24.04-arm`，用和用户相同的单程序 AppArmor 配置（见 overview 的[支持的平台](../overview.md#支持的平台)），再运行一条失败即判红的 bwrap 探测，不跳过。不把 `kernel.apparmor_restrict_unprivileged_userns` 设为 0：CI 要和用户的设置一致。
- macOS 固定用 `macos-15` 和 `macos-26`（arm64）。
- 另设一个原样的 `ubuntu-26.04` 任务，断言后端报告"不支持"并停止，直到 sandbox-runtime issue #429 修复。runner 的版本固定；不卸载 26.04 自带的 `bwrap-userns-restrict` 来让沙盒运行，那测的是改过的系统。
- 报告记下 runner 的 `ImageVersion` 和内核版本。PR 上各包测试用哪些 runner 见 overview 的 [CI 和真实模型测试](../overview.md#ci-和真实模型测试)。
- 开启沙盒的编码题对比实验只在 Linux 上做：依赖都装在任务镜像里，只能用 Docker，镜像在 Ubuntu 24.04 虚拟机的 Docker 里运行，小规模用 `ubuntu-24.04` runner，大规模用自管的虚拟机，评测环境的隔离由一次性的虚拟机提供。macOS 不做编码题对比，误拦和额外耗时由固定命令集里的 git、包管理器、编译和测试命令覆盖。
- 容器的安全选项：完整模式要新挂载 proc，除 `seccomp=unconfined` 和 `apparmor=unconfined` 外还需要 `systempaths=unconfined`。不用 `enableWeakerNestedSandbox` 和 `--privileged`：它们明显削弱隔离，测出的结果不代表真实的隔离强度。Pier 不能给任务容器加安全选项，所以适配里写一个环境类，经 `--environment-import-path` 加载，追加 compose 文件给 `main` 服务加上这三项；开关沙盒的两组用同一份容器配置，容器先通过同一套逃逸探测，再计入对比结果。
